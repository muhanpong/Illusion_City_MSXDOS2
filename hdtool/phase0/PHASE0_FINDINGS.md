# 0단계 조사 결과 (msxdos2 브랜치)

## 1. 매퍼 포트 직접 접근 — 확인 완료, 위험 없음

이전 계획에 "엔진 파일 몇 곳에 매퍼 포트를 직접 쓰는 코드 후보가 있다"고 적었던 항목을 해소했다.
2바이트 단위(`0E xx`, `D3 xx`) 느슨한 바이트 스캔으로 나왔던 18개 후보를 전부 역어셈블해 문맥을 확인한 결과,
**전부 오탐**이었다. 실제로는:
- 데이터 테이블 중간에서 우연히 일치한 바이트 패턴(예: 디스크1 파일5의 `D3 FF`는 곡선/보간 표 한가운데였다).
- `LD C,0xFF` 뒤에 무관한 산술 명령이 이어지는 경우(`SUB 7` 등, BDOS 호출과 무관).

**결론:** 매퍼 세그먼트 전환은 커널의 `E25B`(그리고 이를 부르는 `E246`/`E24B`/`E030`/`E033` 등 점프 테이블 진입점) 한 곳뿐이다.
세그먼트 번호 변환 패치는 이 한 지점만 손보면 된다. `hook.asm`/런처 설계에서 별도 엔진 패치 지점을 추가로 찾을 필요는 없다.

## 2. 논리 세그먼트 사용 범위 — 하한만 확정, 상한은 미확정

`LD A,n / LD B,m / CALL E030|E033|E246|E24B` 형태로 **리터럴 상수**가 바로 앞에 오는 호출만 정적으로 추출 가능하다.
디스크1의 코드 파일(4,5,7,8,9,10,13,14) 전체에서 이 패턴으로 나온 세그먼트 번호는 **0–18**(19개)이었다.

**한계:** 세그먼트 번호를 변수(예: 테이블에서 읽은 값)로 넘기는 호출은 이 스캔으로 잡히지 않는다. 커널 `E244`–`E27D`의
루프(`DEC (IX-0x3F)` 8회 반복 구조)를 보면 페이지당 최대 8개 구간을 순회하며 세그먼트를 바꾸는 것으로 보이는데,
이런 반복 호출은 상수가 아닐 가능성이 크다. **19는 하한값이며 실제 최댓값은 더 클 수 있다.**

**필요한 다음 작업:** `E25B` 시작 지점에 브레이크포인트를 걸고 게임을 처음부터 끝까지(또는 최소한 디스크 2–8 각각의
시나리오 진입부) 실행하며 A(세그먼트 번호)의 실제 최댓값을 기록해야 한다. 자동 조작이 불안정해 이번 조사에서는
수행하지 못했다. **사람이 직접 플레이하면서 트레이스를 남기는 세션이 필요하다.**

권장: 런처가 요구할 세그먼트 수는 안전하게 **32개(512KB)** 로 잡고, 실기에서 실제로 부족하면 줄인다.

## 3. INF 카탈로그 형식 — 필요한 만큼만 해독, 완전 해독은 불필요로 결론

디스크 2–8의 파일 6(INF)은 이름 붙은 레코드(26바이트: 이름 3바이트 + (시작섹터 u16, 길이 u8)×7 + 끝 u16)
14–31개 뒤에, **같은 3바이트 (시작,길이) 단위가 이름 없이 이어지는 꼬리 구간**이 있다. 꼬리는 3바이트 항목 2개당
0바이트 3개(00 00 00, 구분자 또는 미사용 슬롯)가 오는 형태였다(디스크2 확인).

이 꼬리가 정확히 "어느 파일의 추가 구간"인지까지는 밝히지 않았다. **더 파고들 필요가 없다는 결론이다:**
1단계 계획의 원칙대로, 섹터 조각화는 "발견한 모든 (시작,길이) 구간을 분할점으로 삼고, 어디에도 안 속하는
0이 아닌 섹터는 별도 조각으로 만드는" 방식이라 의미 해석 없이도 정확성이 보장된다. 필요한 것은 **구간 좌표 전부를
빠짐없이 수집하는 것**이지 각 구간이 무엇인지 아는 것이 아니다.

**구간 좌표 출처 확정 목록:**
- 각 디스크 섹터 11 파일 테이블 (번호별 시작·길이)
- INF 이름 레코드의 (시작,길이)×7
- INF 꼬리의 이름 없는 (시작,길이) 목록
- 엔진 내장 표(예: 디스크1 파일7의 0x539 시작 12쌍 로드 표, 파일9의 0xEA00 파일 인덱스)
- 고정 상수: 섹터 0(디스크 라벨), 섹터 0x578+2n(세이브 8슬롯)

**미확인:** 파일14(시나리오)가 섹터 번호를 직접 담고 있는지. 이번 조사에서 손대지 못했다. 다음 조사에서
파일14를 문자열/워드 단위로 훑어 섹터 테이블 파일과 겹치는 시작 섹터 값이 있는지 확인해야 한다.

## 4. DOS2 실행 환경 — ASCII DOS2 부팅 성공 (openMSX)

`kittya` + `ide` 확장(Sunrise IDE BIOS 2.50)에서 ASCII MSX-DOS2가 `A:\>`까지 부팅된다. 처음에 막힌 원인은 세 가지였다.

| 증상 | 원인 | 해결 |
|---|---|---|
| "unsupported IDE command E6/00" 반복, 화면 없음 | 이미지 크기가 16헤드×32섹터 실린더 단위로 안 떨어짐(64.19 실린더) | 크기를 512섹터(1실린더) 배수로 |
| BIOS 배너 뒤 `DI; HALT` | mtools가 넣은 x86 부트 코드를 Z80이 실행 | 부트섹터 0x1E–0x1FF를 MSX 부트 코드로 교체 |
| "Boot error / Press any key for retry" | Nextor용 MSXDOS2.SYS v2.40 "Silent"(2286B)가 ASCII 커널에서 실패 | ASCII 정품 MSXDOS2.SYS v2.31(4870B, `~/.openMSX/diska/`) 사용 |

추가 주의: ASCII DOS2 2.31 커널은 FAT16을 못 읽으므로 테스트 이미지는 FAT12(≤32MB)로 만든다. 250MB 이미지(FAT16)에 부트 코드를 덮어쓰면 FAT16 확장 BPB가 깨져 mtools가 FAT을 잘못 읽는다.

작동하는 테스트 이미지 생성 절차: `img/dos2_fat12.dsk`
```
python3 -c "open('dos2_fat12.dsk','wb').truncate(64*512*512)"   # 64 실린더 = 16MB
mformat -i dos2_fat12.dsk -T 32768 -h 16 -s 32 -c 16 -M 512 -r 8 -v ASCIIDOS2 ::
(부트섹터 0x1E-0x1FF 를 ARMI102_MIDI11.DSK 에서 복사)
mcopy -i dos2_fat12.dsk sys_ascii/MSXDOS2.SYS sys_ascii/COMMAND2.COM ::
openmsx -machine kittya -ext ide  (+ tcl: hda <이미지>)
```

남은 측정: 이 환경에서 TPA 상한과 빈 매퍼 세그먼트 수. 매퍼 할당 API 함수 번호는 여전히 문서 확인 후 확정.

## 5. 실기 관련 확인 필요 사항 (mister-super-expert 회신에서 나온 위험)

p5(MFRSD 위 2GB FAT16 파티션)에 배치한 Nextor 에뮬레이션판에 대해 다음이 미확인 상태로 남았다:
- 그 파티션을 관리하는 커널이 MFRSD의 Nextor인지, 아니면 사용자가 쓰던 "FS-A1GT DOS2-ILLUK" 팩의 내장 DOS2
  커널인지. 후자가 우선이면 `EMUFILE SET`이 거부될 수 있다.
- 그 팩이 어떤 Kanji ROM을 쓰는지, 이번 변환에 쓴 패치 ROM(md5 0ba9ee30…)과 같은지.

MSX-DOS2 버전 작업과는 별개 사안이지만, 같은 실기(FS-A1GT + MMC/SD V4/MFRSD)를 쓰므로 여기 같이 기록한다.

## 6. TPA와 빈 세그먼트 측정 결과 (2026-09-29, openMSX `kittya` 512KB)

도구: `memprobe/memprobe.asm` → `MEMPROBE.COM`. DOS2 매퍼 확장 BIOS(EXTBIO FFCAh, D=4 E=1/E=2, 규약은 `Nextor/docs/DOS2-PIS.TXT` §5)로 표를 읽고, ALL_SEG를 실패할 때까지 실제로 불러 개수를 교차 확인한다(사용자 세그먼트라 종료 시 자동 반환).

| 항목 | ASCII DOS2 2.31 + Sunrise IDE | Nextor 2.1.2 (DOS2 모드) |
|---|---|---|
| TPA 상한 (0006) | D806 | D906 |
| 주 매퍼 슬롯 | 3-0 (83h) | 3-0 (83h) |
| 전체 세그먼트 | 32 | 32 |
| 시스템 할당(TPA 4개 포함) | 11 | (표 미확인, 전체−빈=11) |
| 빈 세그먼트 (표) | 21 | 21 |
| ALL_SEG 실제 할당 | 21개, 04h–18h | 21개, 04h–18h |
| 다른 매퍼 슬롯 | 없음 | 없음 |

해석:
- 게임 환경이 쓸 수 있는 세그먼트는 21개다. 게임은 논리 세그먼트 0–18(19개, 하한)을 쓰고, 바운스 버퍼 1개가 더 필요하다. 합계 20개로 **여유는 1개뿐**이다.
- 19는 정적 조사의 하한이다. 실제 사용이 21을 넘으면 이 설계는 512KB 기계에서 불가능하다. §2의 실측(E25B 추적)이 최우선 확인 사항이 됐다.
- DOS2 TPA 상한은 런처 크기에만 영향이 있다(게임은 별도 세그먼트 세계에서 돈다). 문제 없음.
- 실기 MMC/SD V4 드라이버는 시스템 세그먼트를 더 쓸 수 있다. 실기에서 `MEMPROBE.COM`을 실행해 빈 세그먼트 수를 받아야 한다.

## 7. 세그먼트 사용 실측 (1차, 2026-09-29)

도구: `segtrace/segtrace.tcl`. 원본 게임(플로피, `kittya`)을 돌리며 매퍼 포트 FC–FF 쓰기를 전부 감시했다. 게임 커널(E000–E9FF)이 처음 매퍼를 바꾼 뒤부터만 센다. 부팅 중 BIOS의 RAM 크기 검사 쓰기는 제외했다. 게임이 디스크를 확인할 때 스크립트가 디스크를 자동 교체한다.

범위: 에뮬레이션 약 16분. 디스크 1(타이틀·오프닝·시작)과 디스크 2 초반 플레이. 디스크 3–8은 아직 미포함.

| 페이지 | 쓰인 세그먼트 |
|---|---|
| page 0 (FC) | 03, 05, 12 |
| page 1 (FD) | 02, 04, 05, 06, 0D, 0F, 10 |
| page 2 (FE) | 01, 04, 05, 07, 08, 09, 0A, 0B, 0D, 0E, 0F, 10, 12 |
| page 3 (FF) | 쓰기 없음 |

- 서로 다른 세그먼트 16개: 01–0B, 0D–10, 12. 최댓값 12h(18). 00, 0C, 11은 아직 안 나왔다.
- **모든 쓰기가 PC=E2A7(커널 E25B 경로) 한 곳에서** 나왔다. 정적 조사 결론(매퍼 전환 지점은 하나)이 실행으로도 확인됐다.
- 정적 조사 하한(0–18)과 일치한다. 지금까지는 19개를 넘는 사용이 없다.
- page 3는 바꾸지 않는다. page 0은 03(기본), 05, 12로 바뀐다. 두 환경 설계에서 page 0 세그먼트도 변환 표에 넣어야 한다.

남은 확인: 디스크 3–8 구간. 세이브 데이터로 후반부에 들어가 같은 추적을 반복한다.

## 8. 세그먼트 사용 실측 (2차, 후반 디스크)

사용자 세이브(`userdisk.DSK`)를 불러 디스크 4–8 구간을 오갔다. 에뮬레이션 약 634초. 디스크 3은 세이브가 없어 들어가지 못했다.

| 페이지 | 쓰인 세그먼트 (1·2차 합계) |
|---|---|
| page 0 (FC) | 03, 05, 12 |
| page 1 (FD) | 02, 04, 05, 06, 0D, 0F, 10 |
| page 2 (FE) | 01, 04, 05, 07, 08, 09, 0A, 0B, 0C, 0D, 0E, 0F, 10, 12 |
| page 3 (FF) | 쓰기 없음 |

- 2차에서 새로 나온 것은 디스크 7의 page 2 세그먼트 0Ch 하나뿐이다.
- 합계 17개: 01–10h, 12h. 최댓값 12h(18). 00h, 11h는 한 번도 쓰이지 않았다.
- 모든 쓰기가 여전히 PC=E2A7 한 곳이다.
- 디스크 3 미확인 근거: 게임 코드는 디스크 1에만 있고, 디스크 3의 시나리오 파일(파일 14)은 디스크 4의 것과 바이트 단위로 같다(md5 f31861ee). 디스크 4 구간에서는 새 세그먼트가 없었다.

결론: 실측으로는 논리 세그먼트 0–18(19개) 범위를 벗어나지 않는다. 남은 확인은 번호를 변수로 넘기는 호출 지점의 정적 추적이고, 설계에는 0–18 밖의 번호가 오면 멈추고 알리는 안전장치를 넣는다.

## 9. 세그먼트 번호를 변수로 넘기는 호출 지점 전수 조사

도구: `segcalls/segcalls.py`(분류), `segcalls/callers.py`(호출자 추적).

커널에서 새 세그먼트 번호가 들어오는 입구는 두 개다.
- `E030`(→E246→E25B): A=세그먼트, B=페이지. 이전 값을 스택에 남긴다.
- `E02D`(→E224): IXH=세그먼트, IY=호출할 주소. 페이지는 표 E8F7[세그먼트]. 호출 뒤 원래대로 되돌린다.
- `E033`은 스택의 이전 값만 되돌리므로 새 번호가 들어오지 않는다.

디스크1 코드 파일 전체와 FRAY.DOS에서 호출 지점 214개를 찾았다.

| 분류 | 개수 | 결과 |
|---|---|---|
| 바로 앞에 상수 | 194 | 01–12h 중 상수 |
| file5·file14 섹터 캐시 | 4 | (99B6)>>5 + 5, (99B6)=0–15Fh → 05–0Fh |
| file7 +8BC/+904 | 2 | ((0C58)의 상위 3비트) + 8 → 08–0Fh |
| file7 함수 인자(100B, 573C, 5864, 5938) | 5 | 모든 호출자가 상수 05, 0E, 0F |
| file8 (0831) | 2 | 저장되는 값은 상수 0E, 0F뿐 |
| file9 4664 (IXH 인자) | 1 | 모든 호출자가 IXH=02 |
| **file13 (세그먼트 10h page 1의 캐시/MIDI 모듈)** | 4 | **(432E)>>5, 매퍼 크기에 비례** |

### file13 모듈: 매퍼 크기에 따라 사용량이 늘어난다

> **정정(§13):** 아래 "캐시 끝 = (A+10h)×32"는 곡 캐시가 아니라 그 뒤에 붙는 디스크 섹터 캐시의 끝이다. MIDI 곡 캐시는 매퍼 크기와 상관없이 고정 크기이고, 이 절의 설계 결론("(E8F5)로 상한을 정한다")은 성립하지 않는다.

- 로더가 부팅 때 매퍼 세그먼트 수를 재서 (E8F5)에 둔다. 17(11h) 이상이면 세그먼트 10h에 file13 모듈을 올리고 (008F)=세그먼트 수, 아니면 0.
- file4가 (008F)를 (83FB)에 복사하고, 모듈 진입 4006에 A=(83FB)−10h를 넘긴다.
- 모듈은 캐시 끝 인덱스를 (A+10h)×32로 계산한다. 인덱스 0250h(세그먼트 12h의 뒤쪽 8KB)부터 섹터를 채우고, 세그먼트 = 인덱스÷32이다. **즉 세그먼트 12h부터 (E8F5)−1까지 쓸 수 있다.** 512KB GT에서는 1Fh까지다.
- 모듈은 MIDI 연주기(ARMI 계열)를 세그먼트 12h를 page 0에 올려 0x100에서 실행하고, 세그먼트 11h도 쓴다.
- 커널 E045/E048은 (E8F5)≥11h일 때만 이 모듈을 부른다. E048은 디스크 읽기 래퍼로, 11h 미만이면 바로 BDOS(F37D)로 간다.
- 1·2차 실측에서 13h 이상이 안 보인 것은 FM 음원으로만 돌렸기 때문으로 보인다(MIDI 경로 미실행). 확인 필요.

### 설계에 주는 영향

- 게임의 세그먼트 상한은 (E8F5) 값 하나로 정해진다. **런처가 (E8F5)를 우리가 확보한 논리 세그먼트 수로 설정하면 게임이 스스로 그 안에 머문다.**
- 512KB에서 빈 세그먼트 21개 − 바운스 버퍼 1개 = 20 → (E8F5)=14h. MIDI 조건(≥11h)을 만족하므로 MIDI도 켜진다. 대신 MIDI 캐시는 원래 512KB GT(12h–1Fh)보다 작아진다(12h 뒤쪽 절반 + 13h = 48섹터, 24KB).
- ARMI 디스크의 가장 큰 RCP는 23,038바이트(45섹터)라 들어간다. 다만 모듈이 한 장면의 곡 여러 개를 연달아 캐시에 올리는 구조라 합계가 넘칠 수 있다.

## 10. MIDI 모드 세그먼트 실측 (3차)

원본 게임을 MIDI 음원으로 돌렸다. 게임 시작 → 세이브로 디스크 4–8 → 리셋 → MIDI 오프닝 → 디스크 2 진입까지. 부팅 시 감지 값: (E8F5)=20h, (008F)=20h(캐시/MIDI 모듈 켜짐).

| 페이지 | 쓰인 세그먼트 (MIDI 모드) |
|---|---|
| page 0 | 03, 05, 12 |
| page 1 | 01, 02, 04–10 |
| page 2 | 01, 04–1E |
| page 3 | 없음 |

- 게임 시작 직후 캐시 모듈이 11h·12h를 쓰고, 13h→1Eh를 약 6.4초 간격(세그먼트당 32섹터 읽기)으로 차례로 채웠다. 1Fh는 끝까지 한 번도 쓰이지 않았다.
- 한 번 채운 뒤에는 디스크 4–8을 오가도 범위가 늘지 않았다.
- MIDI 오프닝에서는 page 1에 07–0C, 0E, 0F가 새로 나왔다(FM 모드에서는 page 2로만 쓰던 번호). 모두 이미 쓰인 번호 범위 안이다.
- 모든 쓰기는 여전히 PC=E2A7 한 곳.

결론:
- **MIDI 모드에서 이 게임은 매퍼를 거의 끝(1Eh)까지 쓴다.** 사용량은 부팅 때 감지한 매퍼 크기 (E8F5)에 따라 정해진다(§9).
- DOS2판 런처는 (E8F5)를 확보한 논리 세그먼트 수로 설정해야 한다. 이것이 설계의 필수 요소다.
- 1Eh에서 멈춘 이유(끝 세그먼트를 남기는지, 채울 데이터가 끝났는지)는 아직 확인하지 않았다. §9의 계산대로라면 1Fh까지 가능하다.

남은 확인: 원본에서 (E8F5)를 14h로 강제했을 때 MIDI 모드가 정상인지(캐시가 13h까지만 쓰이고 게임이 문제없이 도는지).

## 11. (E8F5) 강제 시험 (2026-09-29)

도구: `e8f5/force_e8f5.tcl`. 로더 0114h(`LD (E8F5),A`, A=감지한 세그먼트 수)에 브레이크포인트를 걸고 A를 바꾼다. 원본 디스크, 한글 Kanji ROM을 넣은 FS-A1GT 기계(512KB), 키 입력은 스크립트로 넣었다(`e8f5/run_*.tcl`).

### 11-1. E8F5=14h, MIDI 음원 → **캐시가 줄지 않는다**

- (E8F5)=(008F)=(E8F6)=14h, 모듈 진입 4006에 A=04h가 넘어갔다(§9 계산대로라면 캐시 끝은 세그먼트 13h).
- 그런데 "MIDI 초기화중. 1분정도 기다려주십시오" 화면에서 캐시가 **13h→1Eh까지 그대로** 채워졌다. 14h 이상 쓰기가 1272회 나왔다(`e8f5/run_midi14_trace.txt`).
- 이 동안 디스크 1의 **014A–02C8h, 383섹터**를 한 섹터씩(반환 주소 42DF) 읽었다. 앞의 8섹터(014A–0151)는 플레이어 초기화용 첫 항목으로, 인덱스 0250h에 읽었다가 곡 데이터로 덮인다. 곡 데이터는 0152–02C8h 375섹터이고 캐시 인덱스 0250h–03C6h를 차지한다. 03C6h÷32 = **1Eh**. 1Eh에서 멈춘 것은 곡 데이터가 거기서 끝나기 때문이다(§10의 "1Eh에서 멈춘 이유" 해결, 구조는 §13).
- 그 뒤 게임 시작, 디스크 2 진입까지 화면상 정상이었다. 에뮬레이터는 실제 32세그먼트가 있으므로 넘친 쓰기가 드러나지 않았을 뿐이다.

결론: **§9의 "(E8F5)로 게임의 세그먼트 상한을 정한다"는 틀렸다.** (E8F5)는 11h 이상/미만으로 모듈을 켜고 끄는 역할만 하고, MIDI 모드는 크기와 상관없이 세그먼트 00–1Eh(31개)를 쓴다. 512KB GT에서 DOS2의 빈 세그먼트는 21개이므로 **DOS2판에서 원본 방식의 MIDI 모드는 불가능하다.**

### 11-2. E8F5=10h, FM 전용 → 정상, 세그먼트 01–0Fh

- 11h 미만이면 로더가 모듈을 올리지 않고 (008F)=0이 된다. **음원 선택 메뉴가 나오지 않고** 바로 "세이브/오프닝/스타트" 메뉴로 간다(FM 고정).
- 스타트 지점에서 시작 → 디스크 1→2 자동 전환 → 게임 화면·대화까지 정상(`e8f5/run_fm10_*`).
- 쓰인 세그먼트: page 0 03, 05 / page 1 02, 04, 05, 06, 0D / page 2 01, 04, 05, 07, 08, 09, 0A, 0B, 0D, 0E, 0F. **10h, 11h, 12h는 한 번도 안 쓰였다.** FM 모드에서 전에 보였던 10h·12h는 모듈(세그먼트 10h)과 그 연주기(12h) 때문이었다.
- 후반 디스크: 유저 디스크 세이브 8개(해저도시, 사령지구, 생체연구소부지, 환영성내부, 주관구, 티우찬지구, 사이코지구, 토토지구)를 하나씩 불러 각각 약 150초 돌렸다. 디스크 4, 5, 6, 7, 8에 들어갔고 전투·메뉴 화면까지 정상이었다(`e8f5/run_fm10_slots.txt`).
- 합계: page 0 03, 05 / page 1 02, 04, 05, 06, 0D, 0F / page 2 01, 04, 05, 07–0F. **논리 세그먼트 01–0Fh(15개) 안에서 끝난다.** 00h와 10h 이상은 한 번도 없었다. 디스크 3은 세이브가 없어 못 봤다(시나리오가 디스크 4와 같음, §8).

### 11-3. 설계에 주는 영향

| 선택지 | 필요 세그먼트 | 512KB+DOS2(빈 21) |
|---|---|---|
| A. FM 전용: 런처가 (E8F5)=10h로 설정 | 논리 00–0Fh(16개) + 바운스 1 = 17 | **가능, 여유 4** |
| B. MIDI 유지(원본 그대로) | 00–1Eh(31개) + 1 = 32 | 불가능 |
| C. MIDI 유지 + 캐시 모듈 패치(곡 캐시 없이 파일에서 직접 읽기, §13) | 00–12h 19 + 바운스 1 = 20 | 가능. 패치 지점은 §13-4 |

권장: **A로 먼저 구현**하고, MIDI는 필요하면 C를 별도 과제로 한다. A에서 게임이 바꾸는 번호는 01–0Fh이고, page 3는 부팅 때 값(FF=00h)을 그대로 쓰므로 논리 00h도 세그먼트가 필요하다. E25B 변환 표는 16칸(00–0Fh)이다(범위 밖 번호는 멈추고 알리는 안전장치 유지).

## 12. 512KB GT에서 DOS2 세그먼트를 더 확보하는 방법 (2026-09-29)

도구: `memprobe/mpb.asm` → `MPB.BIN`(BASIC에서 `BLOAD"MPB.BIN",R`). 결과를 D000h에 남기고 Tcl로 읽었다. 기계는 FS-A1GT(512KB), 부팅은 R800 DRAM 모드(기본).

### 12-1. 시스템 세그먼트 11개의 정체

| 세그먼트 | 내용 | 확인 방법 |
|---|---|---|
| 00–03h | DOS2 TPA(page 3·2·1·0) | 매퍼 초기값 |
| 19h | MSXDOS2.SYS/COMMAND2 부팅 뒤 추가로 잡힘 | BASIC에서는 빈 22개(04–19h), DOS2 프롬프트에서는 21개(04–18h) |
| 1Ah–1Bh | DOS2 커널 작업영역 | ROM과 일치하지 않음, 내용 있음 |
| 1Ch–1Dh | **MSX BIOS 32KB의 DRAM 사본** | Main RAM과 BIOS ROM 8KB 블록 단위 일치 |
| 1Eh | **SUB ROM 16KB의 DRAM 사본** | 일치 |
| 1Fh | **한자 드라이버 앞 16KB의 DRAM 사본** | 일치 |

1Ch–1Fh는 R800 **DRAM 모드**에서만 쓰이는 ROM 사본이다. 원본 게임 로더는 01F2h에서 `CHGCPU`(BIOS 0180h)를 **A=81h(R800 ROM 모드)** 로 부른다. 그래서 원본은 이 4개를 캐시로 덮어써도 문제가 없었다(실행 중 CPU=R800 확인).

#### 원본 게임에서 이 세그먼트들은 무엇인가

"시스템 세그먼트"는 DOS2 매퍼 장부상의 구분일 뿐이고, 물리적으로는 GT 본체 RAM 512KB(16KB×32)의 일부다. 원본 게임은 DOS2 장부를 보지 않고 포트로 직접 32개를 세어(E8F5=20h) 전부 자기 RAM으로 쓴다.

GT는 내장 디스크 ROM이 DOS2 커널이라, 게임 플로피로 부팅해도 디스크를 보기 전에 BIOS와 커널이 먼저 RAM을 준비한다.

| 세그먼트 | 원본 부팅에서 누가, 언제 | 원본 게임에서는 |
|---|---|---|
| 00–03h | 부팅 때 page 3–0 기본 세그먼트 | 게임의 기본 page 세그먼트(page 0=03, page 3=00) |
| 1Ah–1Bh | 내장 DOS2 커널 초기화(약 7.7초, 디스크 ROM 4AAFh 루프)가 잡은 작업영역 | MIDI 캐시가 덮어씀 |
| 1Ch–1Fh | BIOS가 R800 DRAM 모드용으로 복사한 ROM 사본 | 로더가 `CHGCPU(81h)`로 ROM 모드 전환 → 불필요, MIDI 캐시가 덮어씀 |
| 19h | 원본에는 없음(DOS2판에서 MSXDOS2.SYS/COMMAND2 부팅 때 추가) | 해당 없음 |

근거:
- 로더 0114h 시점의 1A–1Fh 내용이 디스크 없이 BASIC으로 부팅했을 때와 바이트 단위로 같다.
- 게임 시작 뒤 F37D 호출 52회 동안(부팅 후 120초까지) 게임 커널(E000–E9FF) 밖에서 매퍼 포트를 쓴 코드가 없었다. 섹터 단위 읽기(2Fh)에서 커널이 1A–1Bh 작업영역을 쓰지 않는 것으로 보이며, 그래서 덮어써도 괜찮았다.

DOS2판은 게임 중에도 DOS2 파일 입출력을 쓰므로 1Ah–1Bh, 00h, 03h, 19h를 살려 둬야 한다. 1Ch–1Fh는 원본처럼 ROM 모드로 바꾸면 되찾을 수 있다.

### 12-2. 확보 방법

| 방법 | 늘어나는 수 | 비고 |
|---|---|---|
| 런처가 원본과 같이 `CHGCPU(81h)` 후 1Ch–1Fh를 게임 환경에 직접 배정 | **+4** | DOS2 표에는 시스템 소유로 남으므로 ALL_SEG가 아니라 런처가 직접 쓴다. 번호는 내용이 BIOS/SUB ROM과 같은지 비교해 찾는다. DRAM 모드로 돌아가면 안 된다(종료는 리셋). |
| 바운스 버퍼로 DOS2 TPA의 page 2 세그먼트(01h)를 그대로 사용 | +1 | 바운스용 할당이 필요 없어진다. 런처 코드는 page 0/1에 둔다. |
| DOS2 TPA의 page 1 세그먼트(02h)를 게임에 배정 | +1 | DOS2 환경에 있을 때 page 1이 비어 있어도 되도록 해석기 코드를 page 0에 둔다. 위험이 있어 마지막 수단. |
| 19h 반환 | +1? | 누가 잡는지 미확인. 기대하지 않는다. |
| 1Ah–1Bh, 00h, 03h | 불가 | DOS2 커널과 DOS2 환경 page 3·0 |

### 12-3. 모드별 수지

- DOS2가 반드시 남겨야 하는 것: 00h(page 3), 03h(page 0, 전환 코드), 1Ah, 1Bh, 19h → 5개. 게임 환경이 쓸 수 있는 최대치는 32−5 = **27개**(바운스 포함)다.
- FM 전용(A): 00–0Fh 16 + 바운스 1 = 17. 기본 21개로 충분하다. ROM 모드를 쓰면 여유가 4에서 8로 늘어난다.
- 원본 MIDI(B): 00–1Eh 31 + 바운스 = 32(바운스를 01h로 대신해도 31). 최대 27이라 **어떤 방법으로도 4개가 모자란다.** 512KB에서는 불가능하다.
- MIDI 패치(C): 캐시를 없애고 곡 데이터를 파일에서 바로 읽으면 00–12h 19 + 바운스 1 = 20개로 기본 21개에 들어간다. ROM 모드로 +4를 더하면 캐시 일부(최대 4세그먼트)를 남길 수도 있다.
- 하드웨어: 매퍼가 1MB 이상이면(GT 내부 RAM 증설, 또는 MiSTer에서 1MB 이상 GT 팩) 원본 MIDI 방식도 들어간다. 다른 슬롯의 외부 매퍼 카트리지는 E25B 패치가 슬롯 전환까지 해야 해서 작업량이 크다.

## 13. file13 모듈(곡 캐시/섹터 캐시) 구조 (2026-09-29)

대상: 디스크 1 파일 13(섹터 228부터 10섹터, 5KB). 로더가 세그먼트 10h에 올리고 page 1(4000h)에서 실행한다. 4000–401Dh는 점프 표다.
플레이어 코드(모듈 5102h부터 1D1Fh바이트)는 초기화 때 세그먼트 12h의 0100h로 복사되고, page 0에 12h를 올려 실행한다.
결론: **MIDI 곡 캐시를 매퍼 크기에 맞춰 조정하는 코드는 없다.** 매퍼 크기에 따라 달라지는 것은 곡 캐시 뒤의 디스크 섹터 캐시뿐이다.

### 13-1. 진입점과 호출자

| 진입 | 실제 | 호출자 | 역할 |
|---|---|---|---|
| 4006h | 403Fh | file4 80D8h (MIDI 선택 시) | 곡 전부 미리 읽기 + 섹터 캐시 영역 설정 |
| 4009h | 4220h | file4 80E6h (FM 선택 시) | 곡 없이 섹터 캐시 영역만 설정 |
| 400Ch | 4268h | 커널 E048 → E60B (디스크 읽기 래퍼) | 섹터 캐시를 거친 디스크 읽기(플레이어 01BAh) |
| 400Fh | 427Eh | file9 1B33h | 섹터 캐시 초기화(플레이어 02BAh) |
| 4012h | 4172h | 게임 | 곡 A 재생 |

모두 커널 E045(=E5F9)를 거쳐 부른다. (E8F5)<11h이면 E045가 바로 돌아오므로 모듈 전체가 꺼진다(§11-2).
file7에도 같은 점프 표 주소를 부르는 코드가 있지만 IXH=06(세그먼트 6의 다른 모듈, FM 쪽)이라 이 모듈과 무관하다.

### 13-2. 4006h: 곡 전부 미리 읽기 (크기 검사 없음)

인자: A=(83FB)−10h → (4324), B=25h(곡 37개) → (4325), HL=CD00h(곡 표, 항목당 시작 섹터 u16 + 섹터 수 u8) → (4326).
file4가 곡 표를 (760A)+78h에서 6Fh바이트(37×3) 복사해 만든다.

1. 플레이어를 세그먼트 12h로 복사하고, 곡 위치 표 4333h(2바이트×41)를 FFh로 채운다.
2. 곡 표의 첫 항목(디스크 1 섹터 014A–0151h)을 인덱스 0250h에 읽고, 플레이어 초기화(0100h)를 부른다.
3. 인덱스를 0250h로 되돌리고, **37곡을 조건 없이 차례로** 읽는다. 곡마다 시작 인덱스를 4333h[i]에 적는다(4145h 루프, 섹터 읽기는 42ABh).
4. 인덱스 → 위치 변환(428Ch): 세그먼트 = 인덱스÷32, 오프셋 = (인덱스 mod 32)×512. page 2에 올려 읽는다.
5. 이 루프에서 A(매퍼 크기)는 전혀 쓰이지 않는다. 그래서 E8F5를 바꿔도 곡 캐시는 항상 0250h–03C6h(세그먼트 12h 뒤쪽 절반–1Eh)다.

### 13-3. 매퍼 크기가 쓰이는 곳: 디스크 섹터 캐시

- 4113h(4006h 끝)와 4242h(4009h): 끝 = (A+10h)×32, 시작(432A) = 곡 캐시의 끝(4009h에서는 0250h), 크기(432C) = 끝−시작, 최대 5A0h(1440섹터).
- 섹터 캐시 본체는 플레이어 쪽 01BAh(모듈 51BCh)다. 태그 표 02D4h(칸마다 섹터 번호)를 찾아(028Fh) 있으면 캐시에서 복사하고, 없으면 F37D로 읽어 넣는다. 교체는 순번(02CF)이다.
- 512KB 원본: MIDI에서는 0400h−03C7h = 57섹터, FM(4009h)에서는 0400h−0250h = 432섹터.
- **버그성 동작:** 끝 < 시작이면(예: E8F5=14h, MIDI) 뺄셈이 음수가 되고, 부호 없는 비교라 5A0h로 잘린다. 실제 메모리보다 큰 섹터 캐시가 설정된다. §11-1 시험에서는 1Fh 이상 쓰기가 안 나와 드러나지 않았다(실제로 넘치는지는 미확인).

### 13-4. 재생: 곡을 바꿀 때 처음부터 순서대로 읽어 푼다

- 4172h(곡 A): A ≥ 곡 수이거나 현재 곡과 같으면 돌아간다. 4333h[A]가 FFFFh(캐시에 없음)이면 **아무것도 하지 않는다.** 없는 곡을 디스크에서 읽어 오는 코드는 없다.
- 있으면 세그먼트 12h를 page 0, 11h를 page 2에 올린다. (432E)=곡 시작 인덱스로 두고 42E9h로 첫 섹터를 F400h에 복사한 뒤 플레이어 0100h를 부른다(HL=F404h, DE=(F400)=풀린 크기, IX=5102h 출력).
- 플레이어의 바이트 읽기(모듈 5188h)는 F400h 버퍼가 끝나면 42E9h를 다시 불러 **다음 인덱스의 섹터를 F400h로 복사**한다(4KB 슬라이딩 창 0E1Fh를 쓰는 압축 해제).
- 즉 곡 데이터는 곡을 바꿀 때 한 번, 시작 인덱스부터 순서대로만 읽힌다. 재생 중에 캐시를 다시 읽지 않는다.

### 13-5. DOS2판 MIDI 패치 방향 (방식 C)

곡 캐시를 없애고, 42E9h가 캐시 대신 파일에서 섹터를 읽게 한다.
1. 4145h 루프(미리 읽기): 섹터를 읽지 않고 인덱스만 곡 길이만큼 늘린다. 4333h 표는 원래대로 채워지므로 4172h는 그대로 둔다.
2. 42E9h: (432E) 인덱스를 디스크 섹터로 바꿔 F400h로 1섹터 읽는다. 곡 데이터는 디스크 1의 0152–02C8h에 곡 표 순서대로 이어져 있으므로 섹터 = 0152h + (인덱스 − 0250h)다. 단, 초기화 때(13-2의 2)는 같은 인덱스 0250h가 첫 항목(014Ah)을 가리키므로 구분이 필요하다(구현 때 확정).
3. 섹터 캐시: 크기(432C)를 0으로 하거나, 400Ch/400Fh 경로를 끈다. DOS2판에서는 파일 읽기가 빠르므로 필요 없다.
4. 필요한 세그먼트: 00–12h 19개 + 바운스 1 = **20개**. 기본 21개에 들어간다. R800 ROM 모드로 얻는 4개는 여유로 남는다.
5. 속도: 곡을 바꿀 때 최대 45섹터(가장 큰 곡)를 파일에서 읽는다. 원본 플로피는 32섹터에 약 6.4초였다. SD에서는 훨씬 짧을 것으로 보지만 실측은 안 했다.
